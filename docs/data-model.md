# Modelo de dados

Fonte: `apps/api/src/db/schema.ts` (Drizzle, SQLite/D1) e `relations.ts`. Tabelas e colunas em snake_case. Enums são colunas `text` com `CHECK`; booleanos são `integer` 0/1; instantes são texto ISO-8601 UTC (`Date` no código); datas de calendário são texto `YYYY-MM-DD`; `metadata` é JSON em texto. Ids são UUID gerados no código.

## Escrita sem transações

O D1 não tem transação interativa. Escritas com mais de um statement (envio, decisão, lote, undo, configurações, convite) vão num único `db().batch([...])`, que é atômico; a verificação de estado fica no `WHERE` do `UPDATE` (`... and status = 'IN_REVIEW'`), e `returning` vazio vira `INVALID_STATE`.

## Status e transições

`IN_REVIEW → APPROVED | REJECTED | CANCELLED`. `APPROVED → IN_REVIEW` só via undo de lote. Regras em `packages/shared/src/rules/status-transitions.ts`.

## Relacionamentos

- `User` 1—N `Communication` como autor, cobertura e aprovador (três relações nomeadas).
- `User` N—N `Project` via `user_projects`. Conflito e limite de simultâneos olham cada projeto do autor (`communications.projectId` está obsoleto).
- `User` 1—N `LedgerEntry` (saldo de dias).
- `Communication` 1—N `Decision`, 1—N `FlowEvent`.
- `ApprovalBatch` 1—N `Decision`.
